PRÉSENTATION DU PROJET
================================================================================

ENSO Monitor est une application web de visualisation des données climatiques
basées sur l'indice ONI (Oceanic Niño Index) publié officiellement par la NOAA.

L'indice ONI mesure les anomalies de température de surface de la mer dans le
Pacifique équatorial central. Il permet de détecter et classifier les phases :
  - El Niño  : ONI >= +0.5°C pendant au moins 5 saisons consécutives
  - La Niña  : ONI <= -0.5°C pendant au moins 5 saisons consécutives
  - Neutre   : entre ces deux seuils

Utilisateurs cibles : scientifiques, étudiants en climatologie, curieux du climat.

Fonctionnalités prévues :
  - Import automatique des données ONI depuis la NOAA (ETL)
  - Stockage en base de données PostgreSQL
  - API REST (FastAPI) exposant les données
  - Interface web (React) avec graphiques interactifs

--- ÉTAPE 2 : Backend FastAPI - API, configuration, tests (2026-11-04) ---

RÔLE DU BACKEND :
  Le backend est le serveur central de l'application. Il expose une API REST
  que le frontend consommera pour afficher les données. Il sera aussi le seul
  composant à lire/écrire dans la base de données PostgreSQL.

COMMENT FONCTIONNE FASTAPI :
  FastAPI est un framework web Python. Il repose sur deux principes :
  1. Les routes sont des fonctions Python décorées (@app.get, @app.post, etc.)
  2. Les données entrantes/sortantes sont validées automatiquement par Pydantic
  Bonus : FastAPI génère automatiquement une documentation interactive Swagger
  accessible sur http://localhost:8000/docs sans aucun code supplémentaire.

ORGANISATION DES FICHIERS CRÉÉS :
  backend/
  ├── app/
  │   ├── core/
  │   │   └── config.py       → Paramètres de l'application via Pydantic Settings
  │   ├── routers/
  │   │   └── health.py       → Route GET /health (état de l'API)
  │   └── main.py             → Crée l'app FastAPI, charge config, branche routers
  ├── tests/
  │   ├── conftest.py         → Fixture partagée : client HTTP de test
  │   └── test_main.py        → 7 tests des routes / et /health
  ├── .env.example            → Template des variables d'environnement
  └── pytest.ini              → Config Pytest (dossier tests, pythonpath)

COMMENT FONCTIONNE PYDANTIC SETTINGS (config.py) :
  - La classe Settings hérite de BaseSettings
  - Chaque attribut a une valeur par défaut (utilisée si la variable env n'existe pas)
  - Si un fichier .env existe, les valeurs y sont lues automatiquement
  - model_config = SettingsConfigDict(...) définit le fichier .env à lire
  - settings = Settings() crée une instance unique importée partout dans l'app
  - Exemple : si DATABASE_URL est défini dans .env, il écrase la valeur par défaut

ROUTES CRÉÉES ET VÉRIFIÉES :
  GET /         → Retourne nom de l'API, version, lien vers /docs
  GET /health   → Retourne {"status": "ok", "service": "ENSO Monitor API"}

COMMENT FONCTIONNE LE ROUTEUR (health.py) :
  - APIRouter() crée un mini-routeur indépendant
  - On y définit des routes comme sur l'app principale
  - Dans main.py, app.include_router(health.router) branche ce routeur
  - Avantage : le code est organisé par domaine fonctionnel, pas tout dans main.py

COMMENT FONCTIONNENT LES TESTS PYTEST :
  - conftest.py définit une fixture "client" : c'est un TestClient FastAPI
  - TestClient simule des requêtes HTTP sans démarrer de vrai serveur réseau
  - Chaque test reçoit le client en paramètre et fait une vraie requête simulée
  - On vérifie le status_code (200 = OK) et le contenu JSON de la réponse

Fichiers créés :
  - backend/app/core/__init__.py
  - backend/app/core/config.py
  - backend/app/routers/health.py
  - backend/app/main.py         (remplace la version initiale)

Choix techniques justifiés :
  - SettingsConfigDict au lieu de class Config : syntaxe Pydantic v2 moderne,
    évite les warnings de dépréciation
  - pytest.ini avec pythonpath = . : permet à Pytest de trouver les modules
    app.* sans erreur d'import
  - conftest.py pour la fixture client : évite de répéter TestClient(app)
    dans chaque test (principe DRY)
  - Routeur séparé pour /health : prépare l'organisation modulaire du code
    (un fichier par domaine : health, oni, stats...)

INSTALLATION ET LANCEMENT
================================================================================

Prérequis système :
  - Python 3.11+  → vérifier : python3 --version
  - Node.js 18+   → vérifier : node --version
  - PostgreSQL 15+ → vérifier : psql --version

Cloner le projet :
  git clone https://github.com/Baba77DRAME/Enso-Monitor.git
  cd Enso-Monitor

Backend (étape 2 - FAIT) :
  cd backend
  python3 -m venv .venv
  source .venv/bin/activate
  pip install -r requirements.txt
  uvicorn app.main:app --reload
  # API disponible sur http://localhost:8000
  # Doc Swagger   sur http://localhost:8000/docs
  # Route racine  : GET http://localhost:8000/
  # Route santé   : GET http://localhost:8000/health

Frontend (à faire à l'étape 3) :
  cd frontend
  npm install
  npm run dev
  # Interface disponible sur http://localhost:5173

ETL (à faire à l'étape 6) :
  cd etl
  python3 -m venv .venv
  source .venv/bin/activate
  pip install -r requirements.txt

Tests backend :
  cd backend
  source .venv/bin/activate
  pytest

Tests frontend :
  cd frontend
  npm run test
